# Test Planning for Specs

Planning test cases during spec generation for TDD-flagged components.

---

## Purpose

**Define test cases BEFORE implementation** — Know what success looks like before writing code.

This document guides the creation of `## Testing Strategy` sections in specs that cover TDD-flagged components. Test cases are derived from TDD diagrams generated by `/vista:tdd`.

### During Spec Generation (This Document)
- Define test case logic from TDD diagrams
- Document success/failure criteria
- Plan test data requirements
- NO actual test code

### During Implementation (Ralph Loops)
- Write actual test code based on spec test cases
- TDD-flagged components: tests FIRST, then implementation
- Non-TDD components: implement normally

---

## When to Add Testing Strategy

Add a `## Testing Strategy` section to a spec when:
- The spec covers a component listed in `## TDD Candidates` in domain-requirements.md
- The component has TDD diagrams in `arch/tdd-*.mmd`

Do NOT add Testing Strategy for specs that don't cover TDD-flagged components.

## Deriving Test Cases from TDD Diagrams

### From Logic Flow Diagrams (`tdd-*-logic.mmd`)

Each path through the flowchart becomes a test case:

| Diagram Element | Test Case Type |
|----------------|---------------|
| Happy path (top to bottom) | Happy path test |
| Decision diamond → left/right | Branch coverage tests |
| Error terminal nodes | Error condition tests |
| Boundary annotations on edges | Edge case tests |

**Example:**
```
Diagram: tdd-pricing-logic.mmd
  Start → Validate Input → Calculate Base → Apply Discounts → Calculate Shipping → Return Total

Test cases:
1. Happy path: valid input → correct total with discount + shipping
2. Branch: empty cart → EMPTY_ORDER error
3. Branch: subtotal > $50 → free shipping
4. Edge: subtotal exactly $50 → verify threshold behavior
5. Error: negative price → validation error
```

### From Decision Tree Diagrams (`tdd-*-decision.mmd`)

Each leaf node becomes a test case:

| Diagram Element | Test Case Type |
|----------------|---------------|
| Each leaf node | One test case |
| Root-to-leaf path | Test setup + execution |
| Branch labels | Input conditions |

### From State Diagrams (`tdd-*-states.mmd`)

Each transition becomes a test case:

| Diagram Element | Test Case Type |
|----------------|---------------|
| Each transition arrow | State transition test |
| Guard conditions | Conditional behavior test |
| Invalid transitions | Error handling test |
| Terminal states | Completion verification |

## Test Case Template

For each test case in the Testing Strategy section:

```markdown
**[Test Name]** — Input: [specific inputs] → Expected: [specific outputs]
```

Group into categories:

### Happy Path
Tests that verify the primary success scenarios.

### Edge Cases
Tests for boundary conditions and unusual-but-valid inputs.

### Error Conditions
Tests for invalid inputs and error handling.

### Test Data Requirements
List specific data needed:
- Mock objects and their configurations
- Boundary values (exact thresholds, zero, max)
- Invalid data variations

---

## Quality Checklist

Before finalizing a Testing Strategy section:

- [ ] Every path through the TDD logic flow diagram has a test case
- [ ] Every leaf in decision tree diagrams has a test case
- [ ] Every state transition has a test case
- [ ] Boundary values are explicitly tested
- [ ] Error conditions from TDD diagrams are covered
- [ ] Test data requirements are specific (not vague)
- [ ] Each test case has clear input → expected output format

## Example Testing Strategy

```markdown
## Testing Strategy

**TDD Required:** Yes (flagged during planning)
**TDD Diagrams:** `arch/tdd-pricing-logic.mmd`, `arch/tdd-pricing-decision.mmd`

### Test Cases (from TDD diagrams)

#### Happy Path
1. **Valid order with gold tier** — Input: non-empty items + gold tier → Expected: 15% discount + free shipping (subtotal > $50)
2. **Valid order with standard tier** — Input: non-empty items + standard → Expected: no tier discount, standard shipping

#### Edge Cases
3. **Empty order** — Input: empty items array → Expected: EMPTY_ORDER error
4. **Boundary: exactly $50 subtotal** — Input: items totaling $50.00 → Expected: verify shipping threshold (free or standard?)
5. **Single item order** — Input: one item, any tier → Expected: correct calculation

#### Error Conditions
6. **Negative item price** — Input: item with price=-5 → Expected: INVALID_PRICE validation error
7. **Unknown user tier** — Input: tier="platinum" (not in system) → Expected: default to standard tier

### Test Data Requirements
- Mock user with each tier level (standard, silver, gold)
- Order items covering price points: $0.01, $25, $49.99, $50.00, $50.01, $100
- Edge case amounts for shipping threshold
- Invalid data: negative prices, empty strings, null values
```
