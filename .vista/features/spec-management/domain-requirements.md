# Domain Requirements: Spec Management

## Problem Statement

Vista specs are currently a one-shot artifact — generated by `/vista:specs` and consumed by Ralph loops, but there's no formalized process for updating specs as implementation evolves. Specs drift as implementation reveals edge cases, users provide feedback, architecture decisions change, and features get expanded or trimmed. There is no traceability between code and the requirements that drove it.

## Users & Personas

### Agent (Primary)
- The chatting Claude agent during implementation sessions
- Needs to update specs when discovering new requirements or changes
- Needs to know what requirement a piece of code implements

### Developer (Secondary)
- Human user reviewing specs and code
- Needs to understand why a spec changed (audit trail)
- Needs to trace code back to requirements and vice versa
- Needs to search git history for spec-related changes

### Ralph Loop Agent (Tertiary)
- Autonomous implementation agent consuming specs
- Needs stable requirement IDs to reference in code comments
- Needs to know which requirements are current vs deprecated

## Business Objectives

1. **Spec-code traceability** — Bidirectional links between requirements and implementation
2. **Change auditability** — Every spec change has a recorded reason
3. **Git discoverability** — Spec changes are searchable in git history
4. **Low friction** — Updating a spec should take seconds to minutes, not break flow

## Success Metrics

- Every spec requirement has a unique ID
- Every spec change has a changelog entry with reason
- Every spec-related commit uses the `spec()` prefix convention
- Code referencing requirements uses the standard ID format
- Agents are aware of spec-update workflow from session start (via CLAUDE.md/project skill)

## Functional Requirements

### FR-1: Requirement ID System

Requirement IDs are assigned during initial spec generation (`/vista:specs`) and tracked during updates.

**Format:** `{FEATURE_PREFIX}-{CATEGORY}{NUMBER}`

| Category | Code | Example |
|----------|------|---------|
| Functional | F | `RSM-F5` |
| Non-Functional | NF | `RSM-NF2` |
| Business Rule | BR | `RSM-BR1` |

**Rules:**
- Feature prefix is derived from feature name (e.g., `ralph-mcp-tool` → `RMT`, `spec-management` → `SM`)
- IDs are assigned sequentially within each category
- IDs are never reused — deprecated requirements keep their ID with a `[DEPRECATED]` marker
- Each requirement line in the spec must be prefixed with its ID

**Example in spec:**
```markdown
### Functional
1. **SM-F1:** The spec-update skill shall accept a feature name and optional topic name
2. **SM-F2:** Changelog entries shall include date, ID, change description, and reason
3. **SM-F3:** [DEPRECATED] Original requirement text (replaced by SM-F7)
```

### FR-2: Changelog Table

Every spec file includes a `## Changelog` section immediately after the Overview.

**Format:**
```markdown
## Changelog

| Date | ID | Change | Reason | Commit |
|------|-----|--------|--------|--------|
| 2026-02-12 | — | Created | Initial spec generation | — |
```

**Rules:**
- The "Created" entry is added during initial spec generation by `/vista:specs`
- Each subsequent update adds a row at the top (newest first)
- The `ID` column references the affected requirement ID (or `—` for structural changes)
- The `Commit` column is filled by the spec-update agent after committing

### FR-3: Spec-Update Skill (`/vista:spec-update`)

A standalone skill that manages spec modifications.

**Invocation:**
```
/vista:spec-update <feature-name> [topic-name]
```

**Workflow:**
1. **Load context** — Read the feature's domain-requirements.md and relevant spec file(s)
2. **Interactive questioning** — Ask the user what changed and why (via AskUserQuestion)
3. **Determine change type:**
   - **Update** — Modify an existing requirement (change wording, add detail)
   - **Add** — Add a new requirement that emerged during implementation
   - **Deprecate** — Mark a requirement as deprecated (never delete, mark with `[DEPRECATED]`)
4. **Apply changes** — Sub-agent modifies the spec file:
   - Updates/adds the requirement with proper ID
   - Adds changelog entry
   - Updates acceptance criteria if needed
5. **Commit** — Create commit with `spec(feature/topic): description` prefix
6. **Report** — Show what changed and affected code references (if any)

### FR-4: Commit Prefix Convention

All spec-related commits use the format:
```
spec(<feature>/<topic>): <description>
```

**Examples:**
```
spec(ralph-mcp-tool/mcp-tools): added retry limit requirement RMT-F12
spec(ralph-mcp-tool/dashboard): deprecated RMT-F3, replaced with RMT-F7
spec(payment-flow): initial spec generation with 4 topics
```

**Rules:**
- Feature name is always present
- Topic name is present when the change affects a single spec file
- Topic name is omitted for cross-cutting or initial generation commits
- Description includes affected requirement IDs where applicable

### FR-5: Code-Side Traceability

Code comments reference requirement IDs using the format:
```python
# Implements SM-F1: The spec-update skill shall accept a feature name
def update_spec(feature_name: str, topic_name: str | None = None):
```

**Rules:**
- The comment format is `# Implements {ID}: {brief description}`
- This is a convention, not enforced by tooling
- The spec-update agent can optionally grep for `{PREFIX}-{ID}` to show affected code when a requirement changes
- Ralph loops should add these comments during implementation

### FR-6: Integration with `/vista:specs`

The existing specs skill is modified to:
1. **Generate requirement IDs** during initial spec creation
2. **Add changelog table** with "Created" entry to each spec file
3. **Add requirement index** section at the end of each spec file

**Requirement Index format:**
```markdown
## Requirement Index

| ID | Section | Status |
|----|---------|--------|
| SM-F1 | Functional | Active |
| SM-F2 | Functional | Active |
| SM-NF1 | Non-Functional | Active |
```

### FR-7: Project-Setup Integration

The project-setup skill templates are updated to:
1. **CLAUDE.md template** — Adds a "Spec Management" section mentioning the `spec()` commit prefix and `/vista:spec-update` skill
2. **Project skill template** — Adds a "Spec Conventions" section with the requirement ID format and changelog convention

## Non-Functional Requirements

- **NF-1: Low latency** — A single spec update (interactive + commit) should complete in under 2 minutes
- **NF-2: Non-destructive** — Specs are append-only for audit purposes; requirements are deprecated, never deleted
- **NF-3: Backward compatible** — Existing spec files without IDs/changelogs continue to work; the system degrades gracefully
- **NF-4: Platform agnostic** — Works on Windows, macOS, Linux (no platform-specific dependencies)

---

## Constraints & Dependencies

### Dependencies
- `/vista:specs` skill — Must be modified to generate IDs and changelogs
- `/vista:project-setup` skill — Templates must be updated
- Git — Commit prefix convention requires git
- Spec template — Must be extended with Changelog and Requirement Index sections

### Constraints
- Requirement IDs must be deterministic and reproducible (sequential, not random)
- Changelog table must be valid markdown
- No external dependencies beyond what Vista already uses (Python 3.10+, git)

---

## User Experience Requirements

### Discovery
- Agents discover spec-update via CLAUDE.md and project skill at session start
- Agents can also be explicitly asked to run `/vista:spec-update`

### User Journey: Spec Update
1. Agent or user identifies a spec change needed during implementation
2. Agent invokes `/vista:spec-update <feature> [topic]`
3. Skill asks what changed and why
4. Sub-agent modifies spec file with proper formatting
5. Sub-agent commits with `spec()` prefix
6. Agent reports what changed and any affected code references

### Error Scenarios
- Feature doesn't exist → Error with guidance to run `/vista:plan` first
- Spec file doesn't exist → Error with guidance to run `/vista:specs` first
- No requirement IDs in spec (legacy) → Offer to retroactively assign IDs
- Git not available → Skip commit step, warn user
